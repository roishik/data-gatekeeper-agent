# Agent Runtime/Framework Selection for the Data Gatekeeper

**Research date:** 2026-09-14

## Executive Summary

The gatekeeper is a single-tenant, email-triggered, high-privilege service with a *small, fixed* set of tools (Gmail, LinkedIn, maybe a couple more) and one job: verify a request from Instinct, execute it, and reply with an auditable result. That shape argues strongly against a general-purpose "personal agent" runtime (OpenClaw and its clones) and in favor of either (a) a minimal, code-first agent SDK with a hand-built control layer, or (b) no agentic framework at all — a deterministic parser plus a narrowly-scoped LLM call, wired together in plain Python.

Key findings:

- **OpenClaw** (formerly Clawdbot/Moltbot, `openclaw/openclaw`, MIT, 387K+ GitHub stars as of Aug 2026) is a general-purpose, always-on personal agent with a huge attack surface: a critical one-click RCE (CVE-2026-25253, 40,000+ exposed instances, 12,000+ exploitable), several more CVEs (command injection, SSRF, path traversal, prompt-injection-driven RCE), and a skill marketplace where independent scans found roughly 12–20% of published skills were malicious. It is architecturally the *opposite* of what this project wants: broad default permissions, a plugin ecosystem you cannot fully audit, and a large always-changing codebase (~430K+ lines). It can be hardened (disable the marketplace, run in a container, strip skills, keep the gateway off the WAN) but you end up fighting the framework's defaults rather than benefiting from them. Not recommended as the base, even hardened. **Fit: 2/10.**
- **Lightweight OpenClaw-inspired clones — nanobot (`HKUDS/nanobot`, MIT, ~1000-line core + broader repo) and NanoClaw (`nanocoai/nanoclaw`, MIT, runs natively on the Claude Agent SDK)** — are much closer to what's needed: native IMAP/SMTP or Resend email channels, container/OS-level sandboxing, credential vaulting, SSRF whitelisting, `allowFrom` sender allow-lists. They're good *evidence* that a small, auditable, email-native agent is buildable, and worth reading as reference implementations, but adopting either as a dependency still means trusting a third-party project's security posture and roadmap for your most sensitive component. **Fit: 5.5–6/10** if you fork and strip further; better used as a design reference than a base.
- **Claude Agent SDK** (Anthropic, open-source client, pay-per-token) gives you the agent loop, tool/permission gating, hooks (pre/post-tool-use deny hooks), subagents, and native MCP support, without any messaging/plugin ecosystem baggage. It's a good fit for the *execution* half of the gatekeeper (the part that, once a request is verified, actually calls Gmail/LinkedIn tools) but it is not a security boundary by itself — hooks are advisory unless you also sandbox the process. **Fit: 7/10** as the tool-execution layer, not as the whole system.
- **LangGraph** (MIT, LangChain Inc.) is the strongest fit for the *control plane*: an explicit, deterministic graph gives you real control-flow integrity (the LLM can't wander outside defined nodes/edges), first-class `interrupt()`/checkpointing for human-in-the-loop approval gates before irreversible actions (send email, post on LinkedIn), and durable state for an always-on service that must survive restarts. LangSmith adds tracing/audit on top, at $39/seat/mo for the Plus tier (free self-hosted framework, paid observability is optional). **Fit: 8/10.**
- **A "no framework" plain Python loop**, or better, **no privileged LLM at all** — a deterministic parser with a strict schema for the incoming email, and the LLM (if used) confined to a quarantined, tool-less role summarizing/classifying untrusted content — is the closest realization of the dual-LLM / CaMeL pattern and gives you the smallest, fully-auditable attack surface. This is more build effort up front (you own the loop, the retry logic, the audit log) but for a fixed, small tool set it's not much code, and it's the only option where you can reason precisely about what can go wrong. **Fit: 9/10** for the security-critical control path, paired with the Claude Agent SDK or a plain Messages API call for the "do the task" step.
- **Managed options** (Anthropic Managed Agents, Cloudflare Agents SDK with native Email Service, n8n self-hosted) are worth a look for infra convenience. Cloudflare's Agents SDK has genuinely native email handling (`onEmail` lifecycle hook, HMAC-signed reply addresses, Durable Object per thread) and would let you skip building your own IMAP/SMTP plumbing, at the cost of Cloudflare lock-in. n8n self-hosted is mature and free for internal use but is a visual low-code tool, a worse fit for a security-critical component you want to reason about in code and review line-by-line. Anthropic Managed Agents (self-hosted sandboxes, beta since May 2026) is aimed at coding-agent-style workloads, not personal-assistant-with-credentials use cases, and adds a vendor control-plane dependency you don't need for a single-user service.

**Bottom line recommendation:** Do not build on OpenClaw or any "big general agent" runtime. Build the gatekeeper as a small, custom Python service: a deterministic email-intake/verification layer (schema validation, sender allow-list, HMAC/signed-thread checks) feeding a LangGraph state machine for the control flow (explicit nodes, human-approval interrupts before any external action), which calls the Claude Agent SDK (or a bare Messages API tool-use loop) only for the narrow "read this quarantined content and extract structured intent" and "call this one approved tool" steps. This combines LangGraph's control-flow integrity and audit trail with the Claude Agent SDK's clean tool/permission model, while keeping the codebase small enough that you — not a framework maintainer — are the one who understands every code path with credentials in it.

## Detailed Notes by Option

### OpenClaw (formerly Clawdbot / Moltbot)

`openclaw/openclaw`, MIT license, 387,800+ stars as of Aug 2026 ([Wikipedia](https://en.wikipedia.org/wiki/OpenClaw), [GitHub](https://github.com/openclaw/openclaw)). Architecture: gateway + hub-and-spoke sessions + plugin/"skill" system, connecting to WhatsApp, Telegram, Slack, Discord, Signal, iMessage, and more, with shell/file/browser/camera access ([innFactory architecture writeup](https://innfactory.ai/en/blog/openclaw-architecture-explained/), [DigitalOcean overview](https://www.digitalocean.com/resources/articles/what-is-openclaw)). Email is supported via a community plugin and IMAP/SMTP configuration, not a first-party hardened channel ([openclaw-email-channel plugin](https://github.com/aibot505/openclaw-email-channel), [Clawly setup guide](https://www.clawly.org/how-to/connect-email)).

Security track record in 2026 is the central reason to avoid it here:
- **CVE-2026-25253**: critical one-click RCE — the Control UI blindly trusts a `gatewayUrl` URL parameter and auto-connects, leaking the auth token; 40,000+ exposed instances found, 12,000+ confirmed exploitable ([ProArch](https://www.proarch.com/blog/threats-vulnerabilities/openclaw-rce-vulnerability-cve-2026-25253)).
- Additional CVEs: command injection (CVE-2026-24763), SSRF (CVE-2026-26322), path traversal (CVE-2026-26329), prompt-injection-driven code execution (CVE-2026-30741) ([Giskard summary](https://www.giskard.ai/knowledge/openclaw-security-vulnerabilities-include-data-leakage-and-prompt-injection-risks)).
- Marketplace ("ClawHub") malware: independent researchers found ~12% of 2,857 published skills were malicious, with later scans reporting ~20% (800+) of the registry as malicious ([TradingView/Reuters](https://www.tradingview.com/news/reuters.com,2026-03-26:newsml_ACN105904:0-openclawd-ships-verified-skill-screening-after-security-researchers-find-12-of-openclaw-marketplace-skills-are-malware/), [Unit 42](https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/)).
- Academic red-teaming: "Trojan's Whisper" demonstrates stealthy manipulation via injected bootstrapped guidance ([arXiv 2603.19974](https://arxiv.org/pdf/2603.19974)).
- Anthropic itself temporarily banned OpenClaw and other third-party harnesses from using Claude subscriptions in April 2026 over abuse/cost concerns, later reinstating access under a separate metered credit pool ([TechCrunch](https://techcrunch.com/2026/04/10/anthropic-temporarily-banned-openclaws-creator-from-accessing-claude/), [VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch)) — a signal about how the project is perceived by the model vendor you'd be relying on.

Hardening guidance exists and is fairly mature (disable the marketplace or curate it yourself, disable filesystem/shell/browser skills, pin versions, keep the gateway off the WAN, run in Docker) ([Cloud Security Alliance hardening guide](https://labs.cloudsecurityalliance.org/agentic/agentic-openclaw-hardening-guide-v1/), [SentinelOne ClawSec](https://www.sentinelone.com/blog/clawsec-hardening-openclaw-agents-from-the-inside-out/), [Repello AI checklist](https://repello.ai/blog/technical-best-practices-to-securely-deploy-openclaw)), but the CSA guide itself notes a malicious skill can evade all eight open-source skill scanners tested — i.e., even with best-practice hardening, the platform's plugin trust model remains a structural weakness. For a component that holds Gmail OAuth and a LinkedIn password, adopting a codebase with this CVE and supply-chain history — even heavily stripped down — is a bad trade versus building narrower from the start.

### Lightweight clones: nanobot and NanoClaw

**nanobot** (`HKUDS/nanobot`, MIT, ~34.6K stars as of Mar 2026): a from-scratch, small (core reported at roughly 1,000 lines) Python agent with channels (CLI/WebUI/chat apps/**email**), a `MessageBus`, `AgentLoop`/`AgentRunner`, pluggable LLM providers (OpenAI, Anthropic, Azure, Bedrock, local), and a two-tier memory system. Security features per its own docs (verified via DeepWiki): workspace restriction for tools, an SSRF whitelist for outbound fetches, optional `bubblewrap` sandboxing for the shell/`exec` tool, per-channel `allowFrom` sender allow-lists (empty list = deny all by default), path-traversal protection, and encouragement to reference secrets via env vars rather than committing them. Email is a first-class channel: IMAP polling + SMTP sending, gated by `consentGranted` and `allowFrom` ([DataCamp tutorial](https://www.datacamp.com/tutorial/nanobot-tutorial), GitHub `HKUDS/nanobot`).

**NanoClaw** (`nanocoai/nanoclaw`, MIT, ~22K stars as of Mar 2026): built natively on Anthropic's **Claude Agent SDK**. Host process (Node.js) manages channels/routing/container lifecycle; each session gets its own Docker (or Apple Container on macOS) with an `agent-runner` that polls a per-session SQLite `inbound.db`/`outbound.db` — no shared mutable state between host and container beyond that. Email is supported via **Resend**. Security is materially stronger than OpenClaw's: unprivileged container user, fixed mount set with a user-managed allowlist (symlinks resolved to block traversal), a credential vault ("OneCLI Agent Vault") that injects real API keys only at the network gateway so raw secrets never enter the container, opt-in egress lockdown (containers placed on a Docker `--internal` network with no internet access except through the vault gateway), and a tiered permission system (Owner/Global Admin/Scoped Admin/Member) ([GitHub `nanocoai/nanoclaw`](https://github.com/nanocoai/nanoclaw), verified via DeepWiki).

Both are legitimate, much closer fits than OpenClaw, and both are worth reading in detail as reference architectures — NanoClaw's credential-vault-plus-egress-lockdown pattern in particular is close to what a Gmail/LinkedIn-holding gatekeeper needs. The reservation about adopting either wholesale is ordinary third-party-dependency risk: you'd be trusting a young (2026), single-maintainer-scale project's security posture for your most sensitive service, rather than a codebase you wrote and can fully reason about. Forking one (most likely NanoClaw, since it already sits on the Claude Agent SDK) and stripping it to exactly the tools/channels needed is a reasonable middle path if you don't want to write the container/IPC/vault plumbing yourself.

### Claude Agent SDK

Reached stable 1.0 on Sept 29, 2025, actively developed through 2026 ([hidekazu-konishi.com guide](https://hidekazu-konishi.com/entry/claude_agent_sdk_complete_guide.html)). Gives you `query()` and the full agent loop: built-in tools, permission gating (allow/ask/deny), MCP support, hooks (including deny-hooks that can block an operation before execution, even mid-session settings edits), subagents, and provider routing. As of 2026 there's also a standalone `@anthropic-ai/sandbox-runtime` package and native OS-level sandboxing (Seatbelt on macOS, bubblewrap+socat on Linux/WSL2) that extends isolation to the whole process tree including hooks and MCP servers ([DataCamp security guide](https://www.datacamp.com/tutorial/claude-code-security), [Bartłomiej Krupa's 2026 sandbox-ladder writeup](https://bartlomiejkrupa.dev/articles/claude-code-security-sandboxing-2026/)). License: SDK client code is open source and free; you pay only for Claude tokens consumed (Sonnet 5: $2/M input, $10/M output; Haiku 4.5: $1/$5; Opus 5: $5/$25 per [claude.com/pricing](https://claude.com/pricing), verified 2026-09-14 — with heavy caching discounts) ([TrueFoundry Managed Agents pricing breakdown](https://www.truefoundry.com/blog/claude-managed-agents-pricing)).

Fit here: excellent as the "actually call the Gmail/LinkedIn tool" execution layer once a request has been verified — its permission/hook model gives you real per-tool-call gating and audit events, and it's the same SDK NanoClaw is built on. It is *not* by itself a substitute for an explicit control-flow/approval layer: hooks are a place to plug in your own policy, not a policy engine, and nothing in the SDK inherently prevents a compromised or injected agent turn from choosing an unexpected (but permitted) tool. Pair it with an explicit outer control flow (see LangGraph / DIY below) rather than relying on the SDK's own loop as your security boundary.

### LangGraph (+ LangSmith)

MIT-licensed framework (free), from LangChain Inc.; LangSmith Plus tier for hosted tracing/deployment is $39/seat/month with 10,000 base traces included ([TrueFoundry LangGraph pricing](https://www.truefoundry.com/blog/langgraph-pricing), [costbench LangSmith pricing](https://costbench.com/software/ai-observability/langsmith/)). Very mature and widely adopted; overtook CrewAI in GitHub stars in Q1 2026 ([dev.to LangGraph vs CrewAI vs smolagents benchmarks](https://dev.to/pooyagolchian/ai-agents-in-2026-langgraph-vs-crewai-vs-smolagents-with-real-benchmarks-on-local-llms-4ma1)).

Why it fits this project specifically: LangGraph models the agent as an explicit graph of nodes and edges rather than an open-ended tool-calling loop, which is exactly the "control-flow integrity" property the prompt-injection-defense literature calls out as the main structural mitigation (see "Plan-then-Execute" below — LangGraph is explicitly cited as one of the frameworks security researchers use to implement that pattern, [arXiv 2509.08646](https://arxiv.org/pdf/2509.08646)). Concretely for the gatekeeper: a node that parses/validates the inbound email against a schema → a node that checks sender identity/thread signature → a node that (only if valid) invokes a quarantined LLM call to interpret the request → an `interrupt()` node that pauses and waits for your explicit approval before any node that sends email, touches LinkedIn, or otherwise has an external side effect → a node that executes the approved action → a node that composes the audit-log reply. `interrupt()` plus the checkpointer persists full state to a `thread_id`, so an always-on service can restart without losing an in-flight approval gate, and the same checkpoint is what LangSmith uses to reconstruct "what happened" for the audit trail ([LangChain interrupts docs](https://docs.langchain.com/oss/python/langgraph/interrupts), [dev.to on checkpoint-before-irreversible-action](https://dev.to/creeta/one-missing-checkpoint-can-break-every-approval-gate-127k)). This is the single best-fit framework for the *outer control loop* found in this research.

### OpenAI Agents SDK

Open source, free (+ OpenAI token cost). Ships handoffs (multi-agent delegation within one run), `output_type` structured outputs, and input/output guardrails that validate messages before/after the agent runs, plus tool guardrails on individual function-tool calls ([OpenAI Agents SDK guardrails docs](https://openai.github.io/openai-agents-python/guardrails/), [handoffs docs](https://openai.github.io/openai-agents-python/handoffs/)). Technically capable, but the user is committed to Claude — adopting an OpenAI-flavored SDK here adds a second model vendor and a second set of conventions for no corresponding security or capability benefit specific to this task. Only worth it if the plan is to use GPT models for the quarantined/untrusted-content-reading role specifically (some dual-LLM designs deliberately use a *different* vendor/model for the quarantined reader to reduce correlated failure — worth considering, but a secondary decision, not primary).

### Pydantic AI

MIT, free, model-agnostic (20+ providers as of April 2026), v2.0 shipped June 23, 2026 with a "Capabilities API" for composable instruction/tool/hook bundles ([futureagi.com Pydantic AI overview](https://futureagi.com/blog/what-is-pydantic-ai-2026/)). Its core value for the gatekeeper isn't as a competing agent loop but as a *validation layer*: guaranteed typed/validated outputs (the model's response must conform to a Pydantic schema or gets automatically retried) is directly useful for turning "email from Instinct" into a strictly-typed `GatekeeperRequest` object before anything privileged touches it, and for constraining what the quarantined LLM is allowed to emit when reading untrusted Gmail/LinkedIn content. Recommend using it as a component (schema validation, deferred/HITL tool support) inside a DIY or LangGraph-based system, not as the top-level framework.

### Google ADK

Apache 2.0, free. Mature as of 2026 (ADK Go 1.0), graph-based execution engine with native human-in-the-loop nodes, MCP support, and — notably — its own security messaging around "zero-trust AI agents," cryptographic signatures, and gVisor sandboxing when deployed via Google's Agent Runtime/Cloud Run/GKE ([Google Developers Blog: zero-trust ADK](https://developers.googleblog.com/build-zero-trust-ai-agents-with-googles-agent-development-kit/)). Reasonable on paper, but its strongest security properties are realized when deployed on Google Cloud infrastructure specifically, which doesn't match a self-hosted, Claude-centric project. Also introduces a third vendor ecosystem's conventions for no distinct advantage over LangGraph here.

### smolagents

Apache 2.0, Hugging Face, ~1,000 lines, "CodeAgent" architecture: the LLM writes and executes Python code as its primary action mechanism rather than calling predefined tool functions, run in a sandbox ([futureagi.com smolagents glossary](https://futureagi.com/glossary/smolagents/)). This is a poor fit specifically *because* of its core idea: letting an LLM author and execute arbitrary code next to Gmail/LinkedIn credentials is a larger and harder-to-reason-about attack surface than a fixed, enumerable tool set — the opposite of what this project wants. Good tool for prototyping and open-ended data tasks; wrong paradigm for a credential-holding security boundary.

### CrewAI

MIT core + paid Enterprise "AMP" tier, $18M raised, very high production usage (~2B executions/12mo, used by a majority of Fortune 500 in some form) ([Wikipedia CrewAI](https://en.wikipedia.org/wiki/CrewAI), [getpanto.ai stats](https://www.getpanto.ai/blog/crewai-platform-statistics)). CrewAI's core abstraction (a "crew" of role-playing agents collaborating) doesn't match this project's shape at all — the gatekeeper is a single linear pipeline (verify → do one task → reply), not a multi-agent collaboration. Skip.

### CaMeL / dual-LLM / plan-then-execute (pattern, not a product)

Google DeepMind's CaMeL (2025, still the reference design in 2026 literature) pairs a **privileged planner** (never reads untrusted text, emits a plan as a locked-down Python-like DSL) with a **quarantined LLM** (reads untrusted content, e.g. an email body, but holds no tool-calling ability) and a capability-tracking data-flow layer between them ([Simon Willison's summary](https://simonwillison.net/2025/Apr/11/camel/), [ssojet.com writeup](https://ssojet.com/blog/camel-a-robust-defense-against-llm-prompt-injection-attacks)). On the AgentDojo benchmark, CaMeL blocked about 67% of prompt-injection attacks — a real improvement over undefended agents, but *not* a complete solution, worth keeping in mind as a calibration point (defense-in-depth, not a silver bullet). Follow-on 2026 work extends the idea to computer-use agents and formalizes it as "plan-then-execute," explicitly citing control-flow integrity as the reason it resists indirect prompt injection — a crafted email can't make the agent invoke a tool call that wasn't part of the pre-committed plan ([arXiv 2509.08646](https://arxiv.org/pdf/2509.08646), [arXiv 2601.09923 "CaMeLs Can Use Computers Too"](https://arxiv.org/pdf/2601.09923)). No framework ships this turnkey; LangGraph is the closest off-the-shelf substrate for hand-implementing it (see above), and it's directly implementable in a plain Python loop too.

Relevant real-world grounding for why this matters here specifically: indirect prompt injection via email is an active, empirically observed attack class in 2026. A benchmark called LivePI, evaluating agents against live email/production-like interfaces, reported attack success rates of 10.7%–29.6% across frontier models when no defense-in-depth pattern is used ([Sysdig prompt injection guide citing 2026 research](https://www.sysdig.com/learn-cloud-native/prompt-injection)). The three-property risk model researchers use — access to private data + exposure to untrusted content + ability to communicate externally — describes the gatekeeper almost exactly, which is the strongest argument in this whole research pass for treating the CaMeL/plan-then-execute pattern as a requirement, not a nice-to-have.

### Plain Python loop over the Anthropic Messages API

The minimal version of the above: a message-history list, a small fixed JSON-schema tool array, a call to the Messages API, and a dispatch function mapping tool names to your own Python functions — a few hundred lines total for a handful of tools ([dev.to "Your First Tool-Calling Agent With No Framework"](https://dev.to/gabrielanhaia/your-first-tool-calling-agent-with-no-framework-just-the-bare-sdk-3ip3), [dev.to "Building Reliable AI Agents from First Principles"](https://dev.to/mjkloski/you-dont-need-a-framework-building-reliable-ai-agents-from-first-principles-2c4o)). One practitioner's rule of thumb, echoed across multiple 2026 writeups: "if you can describe your agent's control flow in five bullet points or fewer, you probably do not need a framework" — which plausibly describes the gatekeeper's core loop (receive email → verify sender/thread → parse request → [approve] → execute one tool → reply). The security case for this approach specifically: identity for the agent, identity for the human it acts for, an authorization decision at the tool boundary, credentials injected at call time, and a per-tool-call audit event are all things you wire in explicitly rather than inherit as framework defaults you have to trust.

The honest tradeoff versus LangGraph: you get *more* control and a *smaller* dependency footprint, but you also have to build checkpointing/durability and the interrupt/approval mechanism yourself if the service needs to survive restarts mid-approval — not hard, but real work LangGraph gives you for free.

### Managed / platform options

- **Cloudflare Agents SDK + Email Service**: genuinely the most email-native option evaluated. Inbound email routes to a Worker via Email Routing; the Agents SDK exposes an `onEmail()` lifecycle hook per Durable Object (one per thread), replies use HMAC-SHA256-signed return addresses so the correct agent instance handles a reply, and there's a reference app (`cloudflare/agentic-inbox`) showing the pattern end to end ([Cloudflare Agents docs: Email](https://developers.cloudflare.com/agents/communication-channels/email/), [Cloudflare blog: Email for agents](https://blog.cloudflare.com/email-for-agents/), [GitHub `cloudflare/agentic-inbox`](https://github.com/cloudflare/agentic-inbox)). Worth strongly considering *just for the transport layer* (you'd still write your own verification/approval/tool-execution logic on top, possibly still using LangGraph-style control flow inside the Worker or in a backend it calls). The cost is real lock-in to Cloudflare's Workers/Durable Objects/R2 programming model for your most sensitive service, and Email Service was still in public beta in 2026.
- **Anthropic Managed Agents**: self-hosted sandboxes went to public beta May 19, 2026 — tool execution can stay on your infrastructure, but Claude, conversation state, and the work queue run on Anthropic's control plane, reached through outbound-only MCP tunnels ([the-decoder.com](https://the-decoder.com/anthropic-adds-self-hosted-sandboxes-and-mcp-tunnels-to-claude-managed-agents/), [bex.co "Rent the Session or Own the Process"](https://bex.co/blog/2026/09/08/claude-managed-agents-vs-self-hosted-sdk)). This product is aimed at coding-agent-style bursty workloads (open a task, run it, tear down), not an always-on, low-volume, single-user personal service; it also makes the gatekeeper's availability depend on Anthropic's control plane being up, which cuts against the "easy to kill/revoke" requirement (revocation should be under your sole control, e.g. pull an OAuth token or `kill` a local process, not "wait for a hosted control plane to notice").
- **n8n (self-hosted)**: Sustainable Use License, free for internal use, mature, native email-trigger node, self-hosted AI starter kit bundles Ollama/Qdrant/Postgres ([n8n reports](https://n8n.io/reports/2026-ai-agent-development-tools/), [Valence Security n8n security writeup](https://www.valencesecurity.com/saas-security-terms/n8n-security-in-2026-how-to-secure-ai-agent-workflows-and-saas-integrations)). Good for lower-stakes automations; a worse fit here because the workflow logic lives in a visual JSON graph rather than reviewable Python, which works against the goal of being able to read and trust exactly what a credential-holding service does. If self-hosting complexity (IMAP polling, process supervision, etc.) turns out to be the real blocker, n8n is a reasonable fallback for the plumbing, with the actual verification/tool logic still implemented as custom code called from an n8n "Execute Code" node — but that's a compromise, not a first choice.
- **Zapier / Make**: not self-hostable, so they're disqualified outright by the project's own "self-host, hold all credentials yourself" requirement — using either would mean routing Gmail/LinkedIn access through a third-party SaaS control plane.

## Ranked Recommendation (Top 3)

1. **Custom LangGraph control plane + Claude Agent SDK (or bare Messages API) for tool execution, built from scratch.** Explicit graph nodes give you the control-flow integrity that defeats most indirect prompt injection by construction (the model can only ever be in one of your defined states, and a crafted email can, at worst, influence data *within* a node, not jump the agent to an undefined action). `interrupt()`+checkpointing gives you a free, durable "pause here and wait for the human to approve this LinkedIn post / email send" gate — exactly the audit-log-as-approval-record pattern the user wants. Pydantic AI (or plain Pydantic models) for strict schema validation of both the inbound Instinct request and the LLM's structured output. Use the Claude Agent SDK for the actual "call this one Gmail/LinkedIn tool" step, since it's already a clean, well-supported tool-calling harness with hooks for a last-line-of-defense policy check. This is more assembly work than adopting a turnkey agent, but every dependency in the stack is either MIT-licensed, self-hosted, and inspectable, or is Anthropic's own SDK that you're already committed to.

2. **Fork NanoClaw (or nanobot) and strip it down to exactly your tools/channels.** If building the LangGraph control plane from scratch feels like too much for a first version, NanoClaw's existing architecture (container isolation per session, credential vault injecting secrets at the gateway rather than into the agent's environment, opt-in egress lockdown, native email support, and it's already built on the Claude Agent SDK) is a legitimate accelerant — remove every channel except email, remove every tool except Gmail/LinkedIn, and add your own verification/approval gate in front of the `agent-runner`. Real risk: you inherit a young, single-team project's bugs and roadmap changes for your most sensitive service. Mitigate by pinning a specific commit, vendoring it into your own repo rather than tracking upstream, and treating it as "code we forked and now own," not "a dependency we update."

3. **Plain Python loop over the Anthropic Messages API, no framework at all, with the LLM used only in a quarantined (tool-less) role for interpreting untrusted email content.** The maximally minimal, maximally auditable option, and arguably the *most* faithful implementation of the CaMeL/dual-LLM pattern the security research recommends — because you're not routing untrusted content through any general agent loop at all, only through a narrowly-prompted, tool-less summarization/classification call, with all the actual privileged logic (which sender is allowed, which action was approved, which tool gets called) as plain deterministic Python you wrote and can read top to bottom in one sitting. Recommended if the fixed tool set stays small (Gmail + LinkedIn + maybe one or two more) and the team is comfortable owning durability/retry logic themselves (a lightweight state machine, or even just "re-poll the inbox and re-derive state from the email thread" — which the email-log design already makes cheap, since the thread *is* the audit log).

**Why a big general-purpose agent (OpenClaw-style) is worse here, explicitly:** OpenClaw's value proposition — one runtime that can talk to a dozen platforms, run arbitrary shell/browser/file tools, and install community skills to extend itself — is precisely the set of properties this project needs to avoid. The gatekeeper's entire value is that it does a *small, fixed, known* set of privileged things, verified against a strict policy, with every action legible in an email thread. A framework whose architecture optimizes for extensibility and breadth (more channels, more skills, more autonomy) works against auditability and against minimizing what a successful prompt injection or a supply-chain-compromised plugin could do. OpenClaw's actual 2026 track record — a one-click RCE reaching 40,000+ exposed instances, a marketplace where ~12-20% of skills were malicious, and Anthropic itself temporarily cutting off its access to Claude — is not a coincidence of poor luck; it's a fairly direct consequence of that "big general agent" shape. A minimal, purpose-built system is more build effort up front, but the effort buys exactly the property this project is being built to guarantee: you can look at the code and the email thread and know precisely what the agent could have done and what it actually did.

## Open Questions for the User

1. **Exact tool set at launch.** Is it Gmail + LinkedIn only, or should the design assume more services (calendar, other socials) will be added soon? This materially affects whether "plain Python loop" stays comfortable or whether the LangGraph structure earns its complexity sooner.
2. **Approval mechanism.** For human-in-the-loop gates before irreversible actions (sending an email, posting/messaging on LinkedIn), what's the actual channel back to you — a reply to the audit-log email thread, a separate Signal/Telegram ping, a CLI prompt on a machine you're at? This decides whether LangGraph's `interrupt()` is checked via polling an inbox, a webhook, or something else, and how long the gatekeeper needs to durably wait.
3. **Where does "verification" of an Instinct request actually live?** E.g., is every incoming request from Instinct cryptographically signed/authenticated at the transport level (so the gatekeeper only needs to check "is this really from Instinct," not "is this plausible-looking text"), or is verification purely content-based (sender address + heuristics)? This affects how much weight the deterministic parser vs. the LLM needs to carry.
4. **Hosting environment.** Self-hosted on your own hardware/VPS, or leaning toward a platform like Cloudflare Workers (which would make its native Email Service genuinely attractive despite the lock-in)? This changes whether option 1 above should be "your own process on a VPS" or "a Cloudflare Worker + Durable Object using LangGraph-style logic inside it."
5. **Appetite for owning durability/retry logic** vs. wanting a framework (LangGraph checkpointing, or n8n) to handle "what if the process restarts mid-task" for you. Given the email thread already serves as a natural state log, how much of "state" can just be "re-derive from the thread" rather than a separate persisted store?
6. **Model diversity for the quarantined reader.** Worth deliberately using a different, cheaper/different-vendor model (e.g., Haiku, or even a non-Anthropic model) for the tool-less "read this untrusted email/LinkedIn content" step, to reduce the odds that whatever fools the privileged planner also fools the quarantined reader in a correlated way? This is a secondary design choice but worth deciding early since it affects the interface between the two LLM calls.
